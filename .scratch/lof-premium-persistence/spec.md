# LOF 连续正溢价持久化设计

Status: 已实现并交付

## 背景与目标

当前 `/api/v1/lof/list` 不返回 `consecutive_premium`，Web 端将缺失字段回退为 `0`，使所有 LOF 显示为“连续溢价 0 天”。本设计建立可审计的 LOF 日度观测与连续正溢价计算，使页面能够区分真实的零天、历史不足和数据不可用。

## 范围与非目标

范围包括：历史回补、每日观测采集、PostgreSQL 持久化、交易日历、API 持续性契约和 Web 展示状态。

不在范围内：根据盘中估值推断连续性；将连续正溢价表述为可执行套利或确认收益；在普通 LOF 页面触发回补或采集任务；为当前自然年以前构造历史记录。

## 领域规则

- 连续正溢价以连续 A 股交易日的同日可比观测计算。正溢价必须严格大于 `0`。
- 一条同日可比观测必须同时有该交易日的场内收盘价和已公布单位净值。价格日期与净值日期不一致时，不写入观测。
- 周末和沪深交易所共同休市的节假日不构成缺口。
- 当前日有同日可比观测但溢价为零或负数时，连续天数为 `0`，状态为 `complete`。
- 当前日没有同日可比观测时，状态为 `unavailable`，不得返回伪造的零天数。
- 已覆盖交易日中出现采集或上游缺口时，状态为 `partial`；从缺口后的首个正溢价日开始计数，天数为已观测下界。
- 首次回补仅覆盖当前自然年。连续序列触及该年度覆盖起点时，状态为 `partial`，并披露历史覆盖起点。

## 数据模型

### `trading_calendar`

存储沪深交易所共同开市日及其来源版本。以日历日期唯一标识，至少包含开市标识、官方来源 URL、来源版本和导入时间。调度、回补、缺口识别和连续性计算只能使用该表，不能以“工作日”推断交易日。

### `lof_premium_observation`

以 `(fund_code, trading_date)` 唯一。至少记录：基金代码、交易日、收盘价、单位净值、溢价率、价格来源和 URL、净值来源和 URL、价格观测时间、净值公布日期、写入来源（`backfill` 或 `scheduled_capture`）、版本、观测时间和更新时间。

同一基金和交易日的有效上游修订执行可审计幂等更新，不新增第二行；修订后，后续读取自动基于新观测计算。

### `lof_premium_job`

记录回补与日度采集的任务类型、范围、状态、游标、尝试次数、成功数、失败数、最后错误、下次重试时间、开始和完成时间。任务命令通过 PostgreSQL 锁保证同类任务只有一个运行实例。

## 数据来源与采集

- 历史单位净值来自东方财富 `lsjz`。
- 历史场内收盘价来自腾讯日 K 线。
- 两个来源仅按同一交易日的交集配对后才写入观测，并保存各自来源 URL 与导入时间。
- 现有实时路径必须保存上游实际净值日期，禁止用行情时间替代净值日期。
- 首次回补覆盖当前有效 LOF 的全部范围，不按溢价、流动性或套利资格筛选。
- 原始观测保留三年；超期记录按交易日清理，不再参与连续性计算。

## 任务运行

- 每个 A 股交易日的 `20:30` 开始日度采集；每 30 分钟重试，最晚至 `23:30`。
- 任务由 Ubuntu `systemd timer` 或部署平台 Cron 调用可移植命令；Flask 进程内线程和定时器不得负责此调度。
- 首次回补通过受运维控制的一次性命令启动，例如 `lof-premium-backfill --year 2026`。它必须可断点续跑，普通页面不提供触发入口。
- 任务失败不写入零值，不阻塞当前行情读取；页面通过持续性状态呈现影响。

## API 契约

`/api/v1/lof/list` 的每项增加规范字段：

```json
{
  "premium_persistence": {
    "consecutive_positive_sessions": 3,
    "status": "complete",
    "as_of": "2026-08-03",
    "history_started_on": "2026-07-30",
    "reason": null
  }
}
```

`status` 只能为：

- `complete`：当前持续性所需的已覆盖交易日完整；
- `partial`：天数为已观测下界，原因必须说明“历史不足”或具体缺失交易日；
- `unavailable`：当前不存在同日可比观测，天数为 `null` 并提供原因。

Web 将此对象归一化为展示状态。`consecutivePremium` 可以保留为展示派生字段，但不得以 `|| 0` 吞掉 `partial` 或 `unavailable`。

## 页面行为

- `complete` 显示 `N 天`；真实非正溢价可显示 `0 天`。
- `partial` 显示 `至少 N 天` 和“历史不足”。
- `unavailable` 显示 `--` 和具体原因，例如“当日价格与净值日期不一致”。

连续正溢价始终是历史观察指标，不改变现有套利资格判断，也不表示可执行收益。

## 验收标准

1. 有效同日正溢价观测连续三交易日时，API 返回 `3` 和 `complete`。
2. 当前同日可比但溢价非正时，API 返回 `0` 和 `complete`。
3. 当前日不可比时，API 返回 `null` 和 `unavailable`，前端不显示 `0 天`。
4. 周末与交易所休市日不降低连续天数。
5. 已覆盖交易日缺失时，API 返回 `partial` 和缺失原因；补齐后自动重算。
6. 连续序列触及当前年回补起点时，API 返回 `partial` 并披露起点。
7. 同一基金、交易日的重复采集是幂等的；上游修订后更新同一观测并影响后续结果。
8. 回补可断点续跑，外部调度重复触发不会并行执行相同任务。
9. LOF 列表读取不会写入日度观测或触发回补。
