# 设计

## 数据模型

规则库由三类事实组成：

- `lof_execution_rule`：交易所代码、份额类别、渠道、字段名、值、单位、当前生效区间和解析状态。
- `lof_execution_evidence`：原始 URL、标题、来源类型、发布日期、生效区间、文本片段、适用范围及其哈希。
- `lof_execution_job`：全量建库、公告增量与状态刷新的可恢复游标、重试时间和计数。

规则和证据一对多关联。新证据不覆盖旧版本；同一字段的当前值按已确认优先级解析。证据必须显式覆盖目标代码/份额类别，或明确适用于目标交易所全部 LOF。专项公告、合同/招募说明书、管理人产品页、交易所或中登通用规则依次降低优先级；同优先级冲突使字段不可用。

## 采集与解析

全量任务从当前有效 LOF 行情集合建立候选记录。每只基金均写入任务结果：没有符合门槛的材料时记录未获取原因，不生成默认 `T+n`、最低金额或最低份额。

采集器只接收可审计的证据源。文本解析必须同时匹配目标代码或适用范围、场内渠道、字段语义和生效条件。`T+n` 可以读取原文明示值，或由同一证据中的起止日期按 A 股交易日历计算；不能从行业习惯、其他基金、场外渠道或行情日期推断。

静态规则由全量任务建立后按公告增量更新。状态刷新只处理调用时当前有效报价溢价率前 20 的 LOF，在交易日收盘后运行；当日无状态证据时状态过期，但当前有效静态规则保留显示。

## 接口

列表与详情的 `execution` 增加可选字段：

```json
{
  "settlement_timing": {
    "subscription_confirmation": {"status": "verified", "timing_text": "T+1", "source": {}},
    "redemption_payment": {"status": "unavailable"}
  },
  "minimum_order": {
    "subscription": {"status": "verified", "display_text": "100 元", "source": {}},
    "redemption": {"status": "verified", "display_text": "100 份", "source": {}}
  }
}
```

`settlement_timing` 的两个键分别对应场内申购确认和场内赎回到账；名称为既有 Web 可选契约，不表示场外时效。客户端不得推导或回填值。列表显示静态规则不等于可执行套利，只有当日状态及其他既有执行条件完整时才可成为候选。

## 验证

- 模型、优先级、冲突、推导边界、缺失建档和前 20 状态范围的服务端测试。
- 列表和详情 API 契约测试。
- Web 单元测试、构建与真实浏览器检查最低申/赎及 T+n 的桌面/移动展示。
