# 设计

## 上下文

`market_overview` 目前对四个组成数据调用 `fetch_with_cache`，但没有读取请求参数，也没有把强制刷新传给组成调用。其他业务读取端点已经使用相同的 `request.args` 与 `fetch_with_cache(force_refresh=...)` 模式。

## 目标与非目标

**目标：**

- 让综合市场概览与其他读取端点保持一致的 `refresh=true` 语义。
- 保持正常请求的缓存和后台刷新行为。
- 保留现有响应信封和元数据。

**非目标：**

- 不修改缓存 TTL、数据源、SWR 策略或数据库。
- 不新增刷新端点。

## 决策

在 `market_overview` 内解析 `refresh` 布尔值，并将其作为 `force_refresh` 传给四个 `fetch_with_cache` 调用。综合端点的 `source` 和 `cached` 继续沿用可转债温度调用的汇总值，保持既有响应形状。

备选方案是由 Web 分别请求四个端点并在客户端拼装首页数据；这会扩大客户端编排、改变现有首页接口依赖，故不采用。

## 风险与取舍

- [风险] 强制刷新会并发访问多个数据源 → 沿用现有端点限流和数据源封装，不改变服务端并发模型。
- [风险] 四个组成数据刷新耗时不同 → 保持现有同步综合响应语义，由统一请求超时和错误处理负责。

## 迁移计划

部署后，旧客户端不携带 `refresh` 时行为不变；新客户端仅在用户主动点击刷新按钮时携带该参数。回滚只需恢复 `market_overview` 的默认调用参数。
